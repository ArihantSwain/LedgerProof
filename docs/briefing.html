LedgerProof checks whether the invoices behind a cash forecast are trustworthy. The demo agency looks comfortable at $16,000 after two payrolls; an approved credit reduces that to $8,000, and a collection delay reveals a $4,000 shortfall. The useful product is the chain from source evidence to a reviewed correction to an understandable cash decision.

Current state: working local rehearsal; mandatory hosted CREAO execution and Convex deployment are still blocked by account setup. Code and diagrams do not establish live integration or sponsor eligibility.

How LedgerProof works

The problem and intended user

A bookkeeper or fractional CFO serving a small creative agency wants to know whether payroll is covered. A spreadsheet can forecast a collection that is overstated, already partly paid, duplicated in the books, or subject to an unapplied issued credit. LedgerProof investigates those source facts and shows the consequence of a reviewed correction. It does not certify accounts, predict defaults, move funds, or automatically change an external accounting system.

The initial named community is independent bookkeepers and fractional CFOs serving small creative agencies. This is a product hypothesis, not validated customer research. No interviews or traction are claimed.

The complete user journey

  1. Start a workspace. The server creates a random case ID and a high-entropy session token. The browser receives an HttpOnly, same-site cookie; the store retains a hash of the token. Workspaces expire after 24 hours and use synthetic records. Anyone given a workspace share link can review that case; this is a collaboration capability, not a production permission hierarchy.
  2. Inspect the original baseline. The deterministic engine computes 13 explicit weeks from imported invoices, historical receipt allocations, opening cash, and dated obligations. Source dates and cents are authoritative; no language model calculates cash.
  3. Add evidence. A bounded text-based credit-note PDF or one-row receipt CSV is parsed. The server checks the schema, invoice reference, amount, currency, document hash, size, and page limits. It stores the original and extracted text, increments the input version, and invalidates pending findings based on older evidence.
  4. Investigate. The intended investigator is the hosted CREAO agent. The backend passes a complete versioned bundle of records and evidence. The agent identifies discrepancies, cites IDs, requests missing information, and returns findings. The app exposes no approval or posting tool to it. While credentials are unavailable, the user may explicitly choose local deterministic rehearsal. That branch is labeled and is not CREAO evidence.
  5. Validate the result. Runtime schemas reject unexpected types, stale versions, unknown evidence, and record IDs outside the current case. Provider status/result IDs must match the stored provider run. Complete JSON output is required; prose is not silently interpreted as financial authority.
  6. Construct a correction proposal. A supported credit-note finding can create a proposed debit to sales returns and credit to receivables. Receipt and duplicate findings use similarly narrow transaction templates. Source amounts are recalculated from normalized records; the agent cannot manufacture a numerical impact. Duplicate proposals reverse a source entry and preserve the original.
  7. Review the evidence. The reviewer opens extracted text and the original PDF or CSV. Preview cash is labeled unapproved. The reviewer enters a reason and approves or rejects a specific proposal against the expected ledger version.
  8. Post atomically. The state transition checks the version and idempotency key, validates balanced permitted accounts, updates the matching source status, writes the journal entry, records the decision, and appends an application event. In Convex this is intended to execute in a database transaction. In local rehearsal a single-process queue serializes file writes. Repeated or competing decisions cannot post the same correction twice in the tested local store.
  9. Change a scenario. The reviewer may move an expected collection date. This changes cash timing without reversing revenue. An explicit reduced collection assumption is possible through the scoped API; it is a scenario, not a write-off or calibrated prediction.
  10. Explain and export. The cash bridge lists a selected week's opening cash, receipts, obligations, and closing cash. The report export includes forecast, findings, run modes/references, and review events. JSON export is implemented; a customer-facing financial report PDF/XLSX is future work. The briefing PDF documents the product and is not a case accounting report.

The exact demonstration math

State Week 1 Week 2 Week 3
Original baseline $20,000 opening + $20,000 invoice − $12,000 payroll = $28,000 $28,000 − $12,000 payroll = $16,000 $16,000
Approved $8,000 credit $20,000 + $12,000 receivable − $12,000 payroll = $20,000 $20,000 − $12,000 payroll = $8,000 $8,000
Collection moves to week 3 $20,000 − $12,000 payroll = $8,000 $8,000 − $12,000 payroll = −$4,000 −$4,000 + $12,000 receipt = $8,000

Other unpaid example balances collect outside the forecast horizon. Later studio/software obligations are displayed in their real weeks. A deliberate duplicate ledger posting is represented separately from normalized invoices, so it does not cause the forecast to collect a second invoice. This is an intentional distinction between a messy source ledger and economic invoice identity.

Week boundaries are local date-only values, start-inclusive and end-exclusive. Calendar arithmetic avoids DST-hour errors. The shortfall indicator tests closing weekly cash below zero; it is not a guarantee that cash stays positive every day within the week. New matched receipts respect their transaction dates. New pre-horizon receipts explicitly reconcile opening cash; future receipts do not silently increase it.

Why three views of cash exist

Baseline preserves original imported collection assumptions and excludes newly approved credit corrections and scenarios. Revised reflects approved corrections and selected explicit scenario assumptions. Preview shows the effect of pending supported credits and remains separate from posted history. Each correction must pass review before it enters revised cash.

The model records historical invoice/receipt facts separately from collection assumptions. A credit changes the collectible invoice amount and the ledger after approval. A payment delay changes a forecast assumption only. A credit score or risk signal, if ever integrated legitimately, cannot automatically establish a write-off.

State, ownership, and failure behavior

The current bounded workspace is one aggregate with nested typed entities. It contains business, invoices, receipt allocations, credits, sources, obligations, entries, scenarios, runs, findings, proposals, decisions, and events. Convex indexes locate the case and expiry. This makes approval atomicity easy to reason about for a small judge case. It is not a claim that the normalized schema in the full specification has been completed.

Evidence changes increment inputVersion. Approval increments ledgerVersion. Every mutation increments a workspace revision. Reset increments a generation. A result from an old generation is ignored; a result from old evidence is stale. A second reviewer must act against the same expected ledger version, preventing a decision based on obsolete balances.

Submission intent becomes unknown before calling CREAO. If the request times out before a provider run ID is safely saved, the application does not blindly submit another run. Account reconciliation is needed. If a run ID is saved, retrieval can resume against that same ID. Retrieval outages are retryable; malformed terminal results become needs_review. No webhook is enabled. Scheduled polling and bounded model-output repair remain unfinished; the present browser/API polling drives retrieval.

The agent instructions exclude document-borne commands. The code escapes source text and accepts only supported structured fields. Offline prompt-injection tests confirm that uploaded text cannot itself authorize posting; they do not establish that an untested hosted LLM will resist all injection attacks.

What has and has not been proved

Local tests cover exact forecast values, partial receipts, excess-credit exceptions, journal balance/account checks, competing decisions, session capabilities, reset/stale handling, actual PDF/CSV parsing, and provider-contract mocks. Browser tests exercise the full local review path, shared polling updates, unavailable CREAO, timeout rehearsal, and mobile layout. See EVALUATION.md for current counts.

Not proved: a live hosted CREAO run; a shared successful agent run; actual Claude use; deployed Convex transactions, subscriptions, or components; external sandbox data; Coinbase agent payments; real customer value; sponsor eligibility; production security or accounting completeness. There is no deployed URL, and no external accounting system has been altered.

Future development: from judge demo to a receivables control product

Product direction

The strongest initial product is an evidence-to-cash workbench for independent bookkeepers and fractional CFOs who serve small creative agencies. It should earn a narrow seat: check whether receivables supporting a forecast are correct, prepare defensible adjustments, and let an accountable human decide. “Autonomous CFO” would overstate the scope and permissions of the present system.

The defensible asset is a traceable connection between source documents, normalized facts, corrections, reviewer decisions, and forecast effects. A generic finance chat interface is easy to replace. A reliable review workflow integrated into month-end close and weekly cash planning may be useful; that value still needs customer validation.

No timeline below is a delivery promise. Effort is an initial engineering estimate assuming one experienced builder and available accounts. Existing blocked integrations must be proved before expanding them. Do not add integrations to increase a sponsor count.

Immediate engineering priorities

Prove CREAO before elaborating it. Create one saved investigator with a clearly named bundle input. Confirm whether the actual account uses agent-v1 or developer-v2, then choose that family explicitly. Retain real status envelopes, model metadata if available, input/output, and share links with secrets removed. Show changed credit amounts and an evidence-bound challenge. No automatic fallback between API families. If the account cannot invoke externally, record the exact blocker rather than replace CREAO with local chat.

Make execution durable. Introduce a Convex Workflow or equivalent persisted scheduler for retrieval, validation and review pauses. Store bounded input hashes, provider IDs, attempts, deadlines and next retry time. Separate retryable retrieval from unknown submission outcome. Keep external actions idempotent where documented; otherwise reconcile. A workflow framework does not make an external non-idempotent call safe to repeat. Use notifications only with explicit user authority.

Finish imports before broadening finance. Build a staging area with field mapping, validation errors, cross-record reconciliation, and an all-or-nothing commit. Preserve originals and parser versions. Require explicit opening cash cutoffs, allocated receipt identity, and dated obligations. Handle partial allocations, credit-note identity, invoice aliases, duplicates, and overpayments as modeled exceptions. Support a deliberately limited USD service-business schema first; reject unsupported inventory or currency semantics.

Normalize persistence when aggregate limits matter. Move business entities to scoped indexed Convex tables without losing atomic approval semantics. Keep decisions, journal lines, source links and event appends in one transaction. Snapshot the exact forecast inputs/results used for a review. Add migrations, pagination, file cleanup, expiry cleanup, and cost/size bounds. Do not market an application event log as immutable cryptographic evidence.

Harden extraction. Run untrusted PDF parsing outside the request process with time/memory/page budgets. Add OCR only after evaluating scans, and retain field provenance and uncertainty. A structured Claude extraction step is justified only if it improves the supported document cases and is actually measured. Make model/provider versions observable. Conflicting fields must remain review items rather than guessed “best” values.

Customer validation plan

Start with five independent bookkeepers or fractional CFOs who serve small creative agencies. Recruit only through authorized outreach; none has been contacted. Ask them to describe their last receivables discrepancy and payroll planning workflow before showing the demo. Record current tools, frequency, review duration, source availability, error cost, and approval responsibilities. Obtain consent before recording or handling real records.

Then run a moderated task using synthetic data first: find the credit, inspect source, decide, explain the cash effect, and challenge a finding. Observe completion, misunderstanding, and time; do not lead the participant to the expected answer. A later pilot may use redacted records under an appropriate agreement. Keep time saved, acceptance rate, false positives and data-cleanup effort separate. A positive interview is not a paying customer or proof of retention.

Production architecture direction

Use organization → business → case ownership, with viewer/preparer/reviewer/admin roles and a formal authorization matrix. Replace shared bearer editing links with revocable scoped invitations for production. Keep demo and customer environments separate. Add environment-specific keys, minimum data retention, encrypted storage managed by the selected platform, deletion workflows, original-file access controls, audit export and incident response. Security claims require verification; no certification is implied.

Operate with a Node-capable Next.js host and a genuine Convex deployment. Add native subscriptions or an authenticated server relay, background retrieval workers, limits per organization/provider, observability with sanitized request IDs, model cost budgets, and a deployment rollback plan. Test expiry and restore behavior. Avoid logging raw financial/identity responses or share tokens. A database transaction can make local posting atomic; it cannot make an external payment and local delivery globally atomic.

Commercial angle and distribution hypotheses

Possible packaging: a per-case investigation tool for independent bookkeepers; a recurring multi-client workspace for fractional CFO firms; or an evidence API/report service. Pricing, willingness to pay, market size and channel performance are unvalidated. Do not invent an addressable-market number or an hourly savings figure.

For a per-case hypothesis, contribution margin equals price minus actual extraction, investigator, storage/compute, payment fees, support, and retry costs. For a subscription, model included cases and guard against one heavy user consuming the whole allowance. Measure completion, monthly reuse, churn, support burden and source-import effort before adding automated billing. Accounting firms may be a better initial channel than direct sales to every small agency, but interviews must test that hypothesis.

Explicit stop conditions

Stop adding sponsor integrations if the mandatory live investigator or deterministic review path is not ready. Stop a credit-data path if supported fields do not fit the identity/business story. Stop scraping if evidence is non-public or behind a login/paywall. Stop autonomous posting/payment scope until a separately authorized design, identity policy and controls exist. Stop claiming statements are complete when the trial balance, cutoff or opening balances cannot be reconciled.

Recommended next release

Release 0.2 should prove live CREAO + Convex, finish a narrow reusable import pipeline, produce a complete scoped case report, and add resilient polling. Release 0.3 should support a real read-only pilot with roles, explicit retention, and accountant-reviewed mappings. Reserve secondary statements and payment commerce for later gates. The current product deserves a reliable receivables seat before it asks for a broader finance seat.

Architecture decisions

One investigator boundary: preserve CREAO for substantive investigation; local rules are explicitly rehearsal. Do not use another provider to pretend the mandatory dependency works.

One selected hosted database: Convex remains central by design. Do not add Spacetime just to collect a track. The local filesystem is an offline rehearsal implementation of the store interface and is disabled by default for production hosting.

Money stays deterministic: source-backed amounts, integer cents, dated obligations, narrow balanced entries, explicit exceptions. The investigator supplies cited interpretations rather than authoritative cash numbers.

Human authority is explicit: interpretation, proposal creation, approval, posting and scenario change remain distinct operations. Approval persists with its entry and event. No external book writes or payments are exposed to the agent.

Provider families are explicit: support developer-v2 and agent-v1 as separate selected adapters behind one interface. Never mix casing, forms, IDs, bases or result assumptions. Account confirmation still gates live calls.

Failed verification changes the claim: a malformed terminal result becomes needs_review; a failed retrieval retries the same ID; an ambiguous submission requires reconciliation. Public documentation, credentials, and mock responses never set LIVE_VERIFIED.

New paths must earn their place: the guide reveals possible Factory, Fetch.ai and Figma paths. They remain conditional because no meaningful runtime/tool workflow has been executed. Optional research/voice/commerce must not displace the receivables core.
